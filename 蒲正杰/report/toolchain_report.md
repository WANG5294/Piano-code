# ESP32 AI 辅助数字钢琴与 AI 原生开发工具链

## 技术方案汇报稿

---

### 一、项目背景与目标

各位老师、同学好。今天我汇报的题目是《基于 ESP32 的 AI 辅助数字钢琴与 AI 原生开发工具链》。

本项目来自 2026 年暑假大作业，核心目标有两个：

1. **任务一：数字钢琴**。在 ESP32-D0WD-V3 开发板上实现一台完整的数字钢琴，完成“按键输入 → 音符发声 → LED 反馈”的完整功能。
2. **任务二：AI 原生开发工具链**。设计并实现一套工具链，让 AI 编程助手能够直接与 ESP32 硬件交互，完成文件传输、程序执行、串口监控、错误报告等闭环操作。

这两个任务不是孤立的。数字钢琴是应用载体，工具链是工程基础设施。工具链让 AI 能够“触碰”硬件，而数字钢琴则是检验工具链有效性的工程基准。

---

### 二、硬件平台分析

我们的硬件平台是一块 ESP32-D0WD-V3 开发板，主要外设包括：

| 功能模块 | 主要器件 | 说明 |
|---------|---------|------|
| 微控制器 | ESP32-D0WD-V3 | 执行 MicroPython 固件 |
| USB 转串口 | CP2102N | 程序下载和串口通信 |
| 蜂鸣器 | MLT-5020 | GPIO25，PWM 驱动 |
| LED | LED2 绿 / LED3 红 | GPIO32 / GPIO33，低电平点亮 |
| 按键 | BOOT、9 个钢琴键 | GPIO0 / GPIO5/12/14/18/19/21/22/35/34 |
| 扩展 IMU | MPU6050 | GPIO16/GPIO17，I²C |

在数字钢琴中，我们使用了 7 个音符键和 2 个八度切换键，通过扩展排针引出到 GPIO5、GPIO12、GPIO14、GPIO18、GPIO19、GPIO21、GPIO22、GPIO35 和 GPIO34。蜂鸣器通过 GPIO25 的 PWM 输出驱动，LED 提供低八度/高八度的视觉反馈。原板载 KEY1/KEY2 已废弃，不再作为数字钢琴输入。

### 三、数字钢琴软件架构

数字钢琴采用模块化设计，核心文件包括：

- `hardware_config.py`：集中管理 GPIO、音符频率、八度倍数等硬件配置。
- `buttons.py`：按键驱动，支持内部上拉、边沿检测和去抖。
- `leds.py`：LED 驱动，封装点亮、熄灭、闪烁等操作。
- `buzzer.py`：蜂鸣器 PWM 驱动，支持按频率或音符名播放。
- `piano.py`：数字钢琴核心逻辑，管理八度切换、音符播放和 LED 反馈。
- `main.py`：程序入口，上电自动运行。

功能上，数字钢琴支持 do-re-mi-fa-sol-la-si 七个音符，并通过两个八度键在低、中、高三个八度之间切换，每个八度对应不同的 LED 状态。

### 四、工具链总体架构

本次汇报的重点是 AI 原生开发工具链。我们的核心思路是：**以 MCP 服务器形式，把 ESP32 的硬件操作能力暴露给 AI 编程助手。**

#### 4.1 为什么选择 MCP？

在任务书中，工具链可以通过 MCP 服务器、Codex 插件、Zcode 扩展、OpenCode 扩展或自定义 CLI 等多种形式实现。我们选择 **MCP（Model Context Protocol）服务器** 方案，原因如下：

1. **标准化接口**：MCP 是 Anthropic 推出的开放协议，AI 客户端可以通过统一方式发现和调用工具，无需为每个 AI 助手单独适配。
2. **与 Kimi Code CLI 兼容**：新版 Kimi Code CLI 原生支持 MCP，配置简单，只需要一个 JSON 文件即可注册。
3. **stdio 传输方式成熟**：MCP 服务器通过标准输入输出与客户端通信，适合本地 Python 脚本实现，部署成本低。
4. **扩展性好**：后续增加新工具时，只需要在 MCP 服务器中注册新的函数，AI 客户端会自动识别。

#### 4.2 工具链架构图

```
┌─────────────────┐     MCP / stdio      ┌─────────────────┐     pyserial      ┌─────────┐
│  Kimi Code CLI  │ ◄──────────────────► │  MCP 服务器      │ ◄───────────────► │  ESP32  │
│  （AI 编程助手） │                      │  mcp_server.py  │                  │         │
└─────────────────┘                      └─────────────────┘                  └─────────┘
                                                │
                                                ▼
                                        ┌─────────────────┐
                                        │  ESP32Client    │
                                        │  esp32_client.py│
                                        └─────────────────┘
```

工具链分为两层：

- **MCP 层**（`mcp_server.py`）：负责向 AI 客户端注册工具、解析参数、返回结果。
- **通信层**（`esp32_client.py`）：负责串口连接、REPL 交互、文件传输、日志缓存和错误解析。

### 五、技术选型说明

| 用途 | 技术选型 | 说明 |
|------|---------|------|
| 工具链开发语言 | Python 3.14 | 开发效率高，与 Kimi 生态兼容好 |
| MCP 框架 | `mcp` Python SDK（FastMCP） | 简化 MCP 服务器开发，支持装饰器注册工具 |
| 串口通信 | `pyserial` | 成熟稳定，支持 Windows/Linux/Mac |
| 固件烧录 | `esptool` | ESP32 官方推荐的固件烧录工具 |
| 文件传输协议 | MicroPython raw REPL | 不依赖额外固件，直接通过串口写入文件 |
| 异步监控 | `threading` | 后台线程持续监听串口输出 |
| 固件开发 | MicroPython | ESP32 官方支持，Python 语法降低开发门槛 |
| AI 助手 | Kimi Code CLI | 新版支持项目级 MCP 配置 |

这里重点说明两个技术决策：

**第一，文件传输采用 MicroPython raw REPL，而不是 ampy 或 WebREPL。**

原因是我们希望工具链对外部依赖尽量少。raw REPL 是 MicroPython 内置的串口协议，通过发送 Ctrl-A 进入、Ctrl-D 执行、Ctrl-B 退出，即可在 ESP32 上执行任意 Python 代码。我们利用这一机制，把本地文件内容转义后直接写入 ESP32 文件系统。虽然这种方式不适合超大文件，但对于数字钢琴这种小型固件完全足够。

**第二，串口监控使用独立后台线程。**

ESP32 运行过程中会持续输出日志和打印信息。我们在 `ESP32Client` 中启动一个守护线程，定期读取串口数据并缓存到环形缓冲区。AI 可以随时调用 `read_serial_output` 获取最新输出，或调用 `get_logs` 获取最近若干行日志。这种设计避免了 AI 调用工具时遗漏关键输出。

### 七、关键实现细节

#### 7.1 串口连接与 REPL 执行

`ESP32Client` 使用 `pyserial` 打开串口，默认波特率 115200。执行 REPL 命令时，先发送 Ctrl-C 中断当前程序，再发送 Ctrl-A 进入 raw REPL，写入命令后发送 Ctrl-D 执行，最后发送 Ctrl-B 退出 raw REPL。

#### 7.2 文件上传

文件上传通过 raw REPL 执行一段 Python 代码实现：

```python
with open("<remote>", "w") as f:
    f.write("<escaped_content>")
```

上传前会对文件内容中的反斜杠、双引号和换行符进行转义，确保写入 ESP32 的文件内容与原文件一致。

#### 7.3 错误报告

`report_error` 工具会读取最近的串口输出，使用正则表达式匹配 MicroPython 的 Traceback 信息，提取文件名、行号、错误类型和错误消息，以结构化 JSON 返回给 AI。这样 AI 可以直接定位问题并修复代码。

#### 7.4 MCP 注册

使用 FastMCP 的装饰器方式注册工具，例如：

```python
@mcp.tool()
def connect_esp32(port: str) -> str:
    client = get_client()
    return client.connect(port)
```

这种方式简洁清晰，新增工具时只需要添加一个函数和装饰器。

### 八、AI 闭环验证流程

工具链的最终价值在于让 AI 能够自主完成“代码生成 → 自动部署 → 执行观测 → 错误诊断 → 修复迭代”的闭环。

一个典型的闭环场景是：

1. 用户在 Kimi 中说：“连接 ESP32 到 COM5，上传 firmware 下的所有文件，运行 main.py，并监控串口输出。”
2. Kimi 自动调用 `connect_esp32("COM5")` 连接硬件。
3. Kimi 依次调用 `upload_file` 上传所有固件文件。
4. Kimi 调用 `execute_program("main.py")` 启动数字钢琴。
5. Kimi 调用 `read_serial_output()` 读取串口输出。
6. 如果出现 Traceback，Kimi 调用 `report_error()` 获取结构化错误信息。
7. Kimi 根据错误信息修改代码，再次上传并运行，直到功能正常。

这个闭环打破了传统嵌入式开发中“AI 生成代码、工程师手动烧录”的断裂模式，让 AI 真正具备了与物理硬件交互的能力。
